# Backup coverage and recovery prerequisites

Kopia is the backup engine. The AfterGrid administrator can inspect a read-only source plan for the core and each reviewed application, even before installing Kopia. Module plans derive candidate source paths from normalized Compose bind mounts beneath the configured AfterGrid root. A path mapping is not a check of file existence, filesystem permissions, repository configuration, snapshot consistency or restore success. No credentials or Compose environment variables are returned.

| Component | Native Kopia source | Consistency requirement |
|---|---|---|
| Core | /source/data/core | Quiesce background downloads and core or use validated SQLite export |
| Homebox | /source/data/homebox | Stop app or validated native export; preserve worker pepper |
| Grocy | /source/data/grocy | Stop app |
| Kiwix | /source/content/kiwix | Finish downloads and index changes |
| Maps | /source/content/maps | Finish downloads |
| Routing | /source/content/routing | Finish graph operations and downloads; stop routing |
| MeshMonitor | /source/data/meshmonitor | Stop app; preserve worker secrets |
| MicroTAK | /source/data/tak/data and /source/data/tak/backup | Stop app; preserve CA and credentials |
| Kolibri | /source/data/kolibri | Finish imports and stop app |
| Jellyfin | /source/data/media/config and /source/content/media | Stop app; finish media imports; cache excluded |
| DokuWiki | /source/data/notes | Stop app or prevent all edits |
| Reviewed module definitions | /source/modules | Capture with matching release |

Kopia's repository, restore destination and working folders are excluded from its own source plan. Do not configure recursive snapshots of /source/data. Use individual paths. Repository encryption does not replace off-server storage and secure credential retention. Source plans are lexical classifications, not validation of host symlinks or bind mount contents. Review actual sources in native Kopia.

## Missing recovery coverage

Worker state is a separate Docker volume containing sharing settings, jobs, generated secrets and credentials. The current Kopia source mounts cannot access it. The core release, host .env, exact images and recovery metadata also need an explicit recovery workflow. Do not claim complete backups or enable unattended updates from source plans. Native repository initialization, consistent snapshot execution, snapshot verification, policy scheduling and clean-machine restore remain outstanding.

## Native repository setup

Install Kopia, securely save its generated repository password outside the server, and verify the intended filesystem is mounted at the configured backup destination before creating a new repository. In the portal, Check repository connection reads the authenticated native Kopia UI API. Create empty local repository queues a fixed Kopia-only job that refuses a connected/initializing server and a nonempty or unreadable /repository directory. Native Kopia initializes and connects using its default encryption and the generated password. No raw native responses or passwords are returned or logged. Do not concurrently administer the native UI or change mounts during initialization. If the job fails or times out, inspect the native UI before retrying; creation may already have succeeded. Existing repositories, remote storage and different credentials remain native UI workflows; no automatic reconnection or overwrite is attempted. Status reflects the running native server connection, not a repository integrity test or verified snapshot. No snapshot is started by this feature.

## First application-consistent snapshot (Grocy)

The initial managed snapshot is deliberately limited to Grocy's reviewed /source/data/grocy directory. Confirm the repository is connected and no other backup, native administrative operation or host-side file writer is active. The serialized worker records the prior running/stopped state, stops a running app with a 60-second grace period, requires all Compose containers to report exited with code zero, invokes the native Kopia CLI in the running Kopia container, and restarts a previously running app using Compose start without pulling or recreating containers. The CLI uses a bounded five-minute timeout, fail-fast, disabled snapshot actions and disabled snapshot-report notifications. A complete JSON manifest with matching path, nonempty content and no errors or reported exclusions is required. A completed snapshot ID is recorded in the job log. This does not verify repository integrity or restoration. No scheduling is configured. Native policies and direct host operations must not run concurrently; the worker only serializes portal jobs. A worker/host crash can interrupt the restart; inspect interrupted jobs and recover the prior state manually. Failed/partial native snapshots may remain. More applications and core-managed content require distinct consistency tests; worker secrets and exact images are still outside this workflow.

## Isolated Grocy restore verification

Verify latest managed snapshot uses the most recent successful Grocy snapshot job, resolves its exact native manifest ID and rejects missing, incomplete, excluded or oversized snapshots. Restore is limited to 512 MiB of reported file data and a five-minute native timeout. A new private directory under /restore is generated for each attempt, never the production bind mount. The restored data/data/grocy.db must be a regular file under nonsymlink directories with no WAL or rollback journal and at most 64 MiB. A temporary worker copy is opened read-only, with a bounded SQLite integrity check and expected products/users tables. No row contents or credentials are logged. The private restored tree is retained for administrator inspection and manual cleanup; it contains sensitive data and consumes disk space. Do not concurrently change the native repository or restore directory. This checks restore and database integrity, not native app startup, every business record, exact image recovery or backup freshness. It does not unlock unattended updates.

## Core database online export

After setup, Create core database snapshot queues a Kopia-only worker job. The worker resolves exactly one running core container by reviewed Compose labels, invokes a fixed unprivileged export script and snapshots /source/data/core/recovery-export. SQLite online backup makes a consistent copy of core.sqlite3 (up to 64 MiB), removes session records from the copy only, checks integrity and expected schema, and retains the administrator and application settings. It does not copy the live database file directly. Staging is mode 0700 with mode 0600 database and ownership marker; normal completion or snapshot failure triggers cleanup of only that job's fixed export. Interrupted or unrecognized staging is never overwritten; inspect and remove it manually after ensuring no job is running. Credentials and password hashes remain sensitive in the encrypted repository; never expose staging. This is a core database snapshot, not complete core backup. Download state, place indexes, worker secrets, sharing and jobs, release files, host configuration, exact images and restore acceptance remain outstanding. No production data is restored. CI pending.

## Worker state and generated secret snapshot

Create worker state snapshot queues a Kopia-only job. It captures a consistent SQLite online backup of jobs.sqlite3 (jobs, sharing and first-run batch records) under the worker secret lock and copies existing reviewed generated-secret JSON sets. Absent uninstalled module secrets are not generated. Unknown, symlinked, insecurely permissioned or malformed files cause failure; the Kopia secret set must exist. Queued/running jobs become interrupted only in the export, so restoring it will not automatically replay unfinished actions. The bounded version-1 JSON envelope includes the database in base64, the job ID and secret sets. It is transferred via Docker stdin to an exclusively created mode-0700 directory /tmp/aftergrid-worker-export inside the existing Kopia container; no worker volume is mounted into Kopia. The envelope is plaintext while staged (base64 is not encryption), then protected by native repository encryption. The stage is removed on normal completion or ordinary snapshot failure; interrupted staging must be inspected manually. Never schedule native snapshots of staging or concurrently administer Kopia; no values are sent to the browser or logs. The worker database limit is 32 MiB and the envelope limit is 48 MiB. Keep the repository password off-server; storing a copy inside the encrypted repository alone cannot recover it. Core and worker backups are separate capture points, not one atomic system image. This does not verify a restored envelope or apply secrets to a new worker. CI pending.
